# FlashGo 项目说明备份

## 1. 项目定位

FlashGo 是一个面向同城即时配送场景的交易与履约平台，核心参与方包含四类：

- 用户：浏览商户、选择商品、提交订单、支付、查看履约进度
- 商户：维护店铺和菜单、处理订单、备货出餐、等待骑手取货
- 骑手：查看可抢订单、抢单、到店取货、配送送达、完成结算
- 平台管理：统一查看用户、商户、骑手、订单与履约数据，进行运营和风控管理

本项目的目标不是只做一个下单页面，而是搭建一套完整的“交易 + 履约 + 结算 + 管理”主链路平台。

## 2. 最核心的业务能力

### 2.1 用户侧

- 浏览商户列表、商户详情、营业状态、配送范围、起送价
- 浏览菜单分类、商品详情、规格、库存、价格
- 创建订单，填写收货地址、备注、联系方式
- 支付订单，查看订单状态与配送轨迹
- 申请取消订单、申请售后或异常反馈

### 2.2 商户侧

- 维护店铺基本信息、营业时间、配送配置
- 维护商品、套餐、库存、上下架状态
- 接收用户订单并决定接单 / 拒单
- 接单后进入备货流程，等待骑手抢单和取货
- 查看历史订单、结算数据、异常订单

### 2.3 骑手侧

- 查看待抢订单池
- 抢单并绑定订单配送责任
- 到店确认取货
- 配送中更新状态
- 完成送达并参与结算

### 2.4 平台管理侧

- 统一查看用户、商户、骑手、订单基础数据
- 查看订单履约全链路状态
- 查看交易额、履约时效、取消率、异常率等核心指标
- 处理人工干预场景，如异常关单、申诉、退款审核、风控冻结

## 3. 核心业务主链路

这是本平台最重要的一条标准履约链路：

1. 用户浏览商户和菜单，选择商品后提交订单
2. 用户完成支付，订单进入“待商户接单”
3. 商户接单后，订单进入“待骑手抢单”
4. 骑手抢单成功，订单进入“待取货”
5. 骑手到店取货后，订单进入“配送中”
6. 骑手完成送达，订单进入“待结算”
7. 系统完成结算，订单进入“已完成”

这条链路是后续数据库设计、接口设计、消息通知、状态变更审计和数据报表的核心基础。

## 4. 业务边界与关键约束

为保证后续实现一致，先约定以下规则：

- 一个订单同一时刻只能有一个主状态
- 商户未接单前，不能进入骑手抢单阶段
- 骑手未抢单前，不能进行取货
- 骑手未取货前，不能标记配送中
- 订单未送达前，不能进入结算完成
- 订单一旦进入终态，不允许再回退到履约中状态

终态定义如下：

- `CANCELLED`：已取消
- `MERCHANT_REJECTED`：商户拒单关闭
- `SETTLED`：已结算完成

## 5. 核心订单状态机设计

订单表建议至少包含两层状态：

- 交易主状态：对外表达订单当前所处环节
- 扩展子状态：描述更细的履约动作，便于页面展示和日志审计

当前阶段优先先把主状态机定义清楚。

### 5.1 订单主状态枚举

| 状态编码 | 状态名称 | 说明 |
| --- | --- | --- |
| `PENDING_PAYMENT` | 待支付 | 用户已提交订单但尚未支付 |
| `PENDING_MERCHANT_ACCEPT` | 待商户接单 | 用户已支付，等待商户处理 |
| `MERCHANT_REJECTED` | 商户已拒单 | 商户拒绝接单，订单关闭 |
| `PENDING_RIDER_GRAB` | 待骑手抢单 | 商户已接单，等待骑手接单 |
| `RIDER_ASSIGNED` | 骑手已接单 | 已有骑手抢单成功，待到店取货 |
| `PICKED_UP` | 已取货 | 骑手已从商户取到货物 |
| `DELIVERING` | 配送中 | 骑手正在配送 |
| `DELIVERED` | 已送达待结算 | 用户已收货，等待结算入账 |
| `SETTLED` | 已结算完成 | 订单履约完成，进入最终完成态 |
| `CANCELLED` | 已取消 | 用户取消、超时取消或平台取消 |

### 5.2 状态流转规则

```text
PENDING_PAYMENT
  -> PENDING_MERCHANT_ACCEPT   (用户支付成功)
  -> CANCELLED                 (用户主动取消 / 支付超时关闭)

PENDING_MERCHANT_ACCEPT
  -> PENDING_RIDER_GRAB        (商户接单)
  -> MERCHANT_REJECTED         (商户拒单)
  -> CANCELLED                 (用户取消 / 平台取消 / 超时未接单)

PENDING_RIDER_GRAB
  -> RIDER_ASSIGNED            (骑手抢单成功)
  -> CANCELLED                 (商户取消 / 平台取消 / 长时间无人接单)

RIDER_ASSIGNED
  -> PICKED_UP                 (骑手确认取货)
  -> CANCELLED                 (异常取消，需记录责任归属)

PICKED_UP
  -> DELIVERING                (开始配送)
  -> CANCELLED                 (极少数异常取消，需走人工流程)

DELIVERING
  -> DELIVERED                 (骑手确认送达)
  -> CANCELLED                 (配送异常取消，通常需人工介入)

DELIVERED
  -> SETTLED                   (系统结算完成)

MERCHANT_REJECTED              (终态)
CANCELLED                      (终态)
SETTLED                        (终态)
```

### 5.3 建议的状态机约束

- 只有支付成功后，订单才能进入商户接单池
- 同一订单只允许一个骑手抢单成功，抢单操作必须具备并发控制
- 每一次状态变更都必须记录操作人、角色、时间、备注
- 取消订单必须记录取消原因和责任方：用户 / 商户 / 骑手 / 平台 / 系统
- 送达与结算必须解耦：先确认履约完成，再进行资金清分与结算

## 6. 核心订单表设计建议

后续订单主表建议至少包含以下关键字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 订单 ID |
| `order_no` | 业务订单号 |
| `user_id` | 下单用户 ID |
| `merchant_id` | 商户 ID |
| `shop_id` | 店铺 ID |
| `rider_id` | 骑手 ID，未抢单时可为空 |
| `status` | 订单主状态 |
| `total_amount` | 订单总金额 |
| `pay_amount` | 实付金额 |
| `delivery_fee` | 配送费 |
| `merchant_remark` | 商户备注 |
| `user_remark` | 用户备注 |
| `receiver_name` | 收货人 |
| `receiver_phone` | 收货电话 |
| `receiver_address` | 收货地址 |
| `placed_at` | 下单时间 |
| `paid_at` | 支付时间 |
| `merchant_accepted_at` | 商户接单时间 |
| `rider_assigned_at` | 骑手抢单时间 |
| `picked_up_at` | 取货时间 |
| `delivered_at` | 送达时间 |
| `settled_at` | 结算完成时间 |
| `cancelled_at` | 取消时间 |
| `cancel_reason` | 取消原因 |
| `cancel_by_role` | 取消角色 |

除了订单主表，建议同时设计：

- `order_item`：订单商品明细
- `order_status_log`：订单状态流转日志
- `order_refund`：退款 / 取消相关资金记录
- `order_settlement`：平台、商户、骑手结算记录

## 8. 当前阶段的结论

在这个项目里，最重要的不是先写页面，而是先锁定统一业务语言。当前已经明确了三件事：

- 四类角色分别负责什么
- 订单从下单到结算的标准主链路是什么
- 订单状态机如何流转，哪些状态属于终态，哪些状态不允许跳转

## 9. 下一步建议

在这份项目说明的基础上，下一步最适合继续推进的是：
