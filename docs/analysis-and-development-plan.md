# FlashGo 项目分析与开发计划

分析日期：2026-10-29。基线：main / a4bebb0。依据为仓库源码、SQL、pom.xml、README 和业务说明；未启动服务或执行测试。本机 Java 为 17.0.5，未找到 Maven，仓库无 Maven Wrapper。

## 一、总体判断

项目处于“业务建模 + 工程与认证骨架”阶段。已具备四端身份模型、登录接口、JWT 与 Redis 在线态、基础数据库迁移。尚未具备可运行验证的交易履约闭环。README 中的状态机属于设计成果；资源归属校验、订单与结算不能视为已实现。

建议继续采用按业务域组织的模块化单体，先完成一致性明确、可测试的订单闭环，再扩展运营能力。现阶段无需拆分微服务。

README 展示的 merchant、order、platform、product、rider、settlement、shop、user 等业务包，目前没有对应业务实现文件。没有前端项目、容器编排或 CI 文件。

技术依赖包括 MyBatis-Plus 3.5.7、JJWT 0.12.6、Springdoc 2.5.0、Redis、RabbitMQ、Flyway、MapStruct。RabbitMQ 和 MapStruct 目前主要是依赖预置，未见消息生产消费或对象映射实现。本报告不对依赖漏洞或当前版本兼容性作结论，后续需独立检查。

## 三、已有设计的价值

- 四端使用统一登录入口，身份与角色集中定义，方便后续隔离接口。
- 密码通过 BCrypt 校验，没有以明文直接比较密码。
- SQL 具有业务唯一键、外键、金额 DECIMAL 类型、商品名称价格快照和状态日志表。
- 送达与结算分离，适合后续异步结算与补偿。
- Flyway 管理结构演进，有利于环境一致性。

## 五、业务与数据模型补全

现有 11 张表覆盖账户、商户、店铺、骑手、分类、商品、订单、明细、状态日志、结算。足以作为起点，但尚不能完整支撑资金与异常处理。

首版需补齐：

1. 用户地址；订单继续保存收货信息快照，避免地址修改影响历史订单。
2. payment_order、refund_order：商户交易号、渠道交易号、金额、状态、通知摘要、重试与完成时间。
3. 库存预占或库存变动记录：区分下单预占、支付确认、取消释放；每项操作具有唯一业务键。
4. outbox_event 与消费去重记录：确保订单事务提交后消息最终可投递，重复消费无重复副作用。
5. 结算明细或资金流水：收款方、业务来源、金额、规则版本、流水唯一键；账务计算与外部打款分开。
6. 管理审计记录：冻结、取消、退款审核、权限修改等敏感操作可追踪。
7. 按真实列表查询添加组合索引，例如 (user_id, created_at, id)、(merchant_id, status, created_at)、(rider_id, status, created_at)。最终以执行计划验证。

金额使用 BigDecimal，服务端重新计算价格，固定币种和舍入规则。不要把前端金额当作交易依据。新增结构使用 V3 及后续迁移，不改已执行迁移。账号注册、商户入驻与骑手审批可先由平台创建，但须明确首版范围。

## 六、目标实现约束

- controller 负责协议与参数，service 负责业务和事务，mapper 负责持久化；状态流转集中维护。
- 每次订单变更在同一事务中更新订单、写状态日志、写必要 outbox。
- 抢单用数据库条件更新判定唯一胜者，例如状态为待抢且 rider_id 为空才可更新；Redis 用于加速，数据库作为最终约束。
- 库存使用带 stock >= quantity 的原子更新，多商品按稳定顺序处理，失败整体回滚。
- 下单幂等键、支付通知唯一键、退款请求号、结算唯一键各自明确作用域。
- 订单状态、支付状态、退款状态、结算状态分别管理；商户拒单不意味着退款已经完成。
- 订单超时与支付回调竞争通过条件更新与事务裁决；已关单后到账进入退款或人工补偿流程。
- MQ 采用确认、有限重试、死信、告警与人工重放；必须测试重复、延迟、乱序与丢失补偿。
- JWT 的绝对有效期与 Redis 的滑动 TTL 分开说明；续期须有明确接口或重新登录策略。

## 七、分阶段开发计划

估算以两名后端全职开发、测试与运维按需支持为前提。总计约 12—16 周可交付后端试运行版本，含 20% 左右联调与返工空间；真实支付渠道接入时间另受外部资质和联调制约。四端完整前端需要额外排期。

| 阶段 | 时间估算 | 核心任务 | 验收门槛 |
| --- | --- | --- | --- |
| S0 范围与规则冻结 | 2—3 天 | 明确单店单订单、库存策略、配送费、取消窗口、退款责任、抽佣舍入、多端会话、首版账号来源；形成 ER 与 API 草案 | 每条状态转换具备角色、前置条件、资金影响与失败处理 |
| S1 工程可复现 | 3—5 天 | 配置模板、Wrapper、MySQL/Redis/RabbitMQ 本地编排、Mapper 扫描修正、开发种子数据、CI、启动文档 | 新环境可构建启动；Flyway 从空库执行成功；健康检查通过 |
| S2 认证加固 | 1 周 | 会话版本、退出失效、禁用撤权、限制持久化、权限初始化、错误响应、登录限流 | 四端登录成功；过期、篡改、退出后重登旧令牌、跨角色访问均有测试 |
| S3 商品与主体 | 1—1.5 周 | 平台创建主体；商户店铺、分类、商品、上下架；用户浏览与地址；分页和归属校验 | 商户 A 无法读写 B 的管理资源；无效商品不可购买 |
| S4 订单与库存 | 1.5—2 周 | 订单状态机、服务端计价、快照、库存预占、下单幂等、列表详情、取消和超时释放 | 同一请求无重复单；库存不为负；订单与日志一致；失败事务完整回滚 |
| S5 支付退款 | 1—2 周 | 支付适配接口、开发模拟渠道、真实渠道配置隔离、回调验签验额、退款、主动查单与对账补偿 | 重复通知只生效一次；支付与关单竞态可恢复；拒单退款可追踪 |
| S6 商户与配送 | 1—1.5 周 | 接单拒单、待抢池、并发抢单、取货、开始配送、送达、骑手工作状态 | 建议以 100 并发竞争同一单验证仅一人成功；非归属骑手不能推进状态 |
| S7 结算与可靠消息 | 1—1.5 周 | outbox 投递消费、结算规则快照、分账流水、补偿任务、失败查询重试 | 重复消费无重复入账；分配金额符合规则且守恒；MQ 中断恢复后可补齐 |
| S8 平台与可观测 | 1 周 | 订单检索、主体禁用、异常工单、退款审核、统计、审计、请求追踪、指标告警 | 平台操作可审计；无关个人信息脱敏；核心故障能定位 |
| S9 联调与试运行 | 1—2 周 | 四端流程联调、容量基线、故障演练、备份恢复、发布回滚、部署手册 | 全链路与异常用例通过；对账无未解释差异；恢复演练达成预设目标 |

依赖主线：S0 → S1 → S2 → S3 → S4 → S5 → S6 → S7 → S8 → S9。测试、接口文档与运维约束随各阶段完成，不留到末期集中补做。outbox 基础能力应在 S4 建立，S7 完成资金场景与恢复验证。

## 八、首版 API 工作清单

以下为待设计建议，不是当前已有接口。统一 /api/v1 前缀。

| 端 | 建议接口组 |
| --- | --- |
| 认证 | 保留 auth/login、auth/me、auth/logout；按选定策略增加续期与会话撤销 |
| 用户 | GET user/shops、user/shops/{id}/products；地址 CRUD；POST user/orders；GET user/orders 与详情；POST 取消、支付、退款申请 |
| 商户 | 店铺设置；分类和商品 CRUD；上下架；订单列表详情；POST orders/{id}/accept、reject |
| 骑手 | 工作状态；待抢订单池；配送单列表详情；POST grab、pickup、start-delivery、deliver |
| 平台 | 主体创建与禁用；订单查询；异常处理；退款审核；结算查询与受控重试；运营统计 |
| 内部与渠道 | 支付和退款回调；受控超时任务、消息补偿与对账任务 |

所有列表明确分页、排序、过滤范围；所有变更明确幂等、权限、HTTP 状态与错误码。渠道回调通过独立可信校验接入，不依赖用户 Bearer Token。

## 九、测试与上线标准

1. 单元测试：状态转换矩阵、金额分配与舍入、权限规则、非法输入。
2. MySQL/Redis 集成测试：真实迁移、唯一约束、事务回滚、会话失效、库存和抢单竞争；可使用 Testcontainers，不能用内存数据库替代关键 MySQL 行为验证。
3. 消息测试：事务提交前后故障、重复消费、发布失败、消费失败、死信重放。
4. 端到端：四端正常闭环；支付超时；拒单退款；无人接单；配送异常；重复结算；账号禁用。
5. 故障恢复：Redis 不可用时拒绝受保护请求并告警；MQ 中断由 outbox 补发；进程重启不遗漏超时单和待结算单。
6. 容量指标在 S0 按预期订单量和部署资源制定，S9 输出吞吐、P95/P99、错误率、锁等待、慢查询和资源使用的实测基线。
7. 发布前完成配置校验、密钥注入、日志脱敏、数据库备份恢复、迁移验证与应用回滚演练。数据库破坏性变更采用兼容演进。

## 十、后续产品范围
